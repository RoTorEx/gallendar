# Текущие задачи

Рабочий CLI реализован по прямому запросу пользователя. Текущая внешняя задача —
проверка гипотезы и настройка аккаунтов; реальная эксплуатация остаётся после GO. Завершённые задачи удаляются из
очереди; результаты проверки сохраняются в [business/validation.md](business/validation.md).

## 1. Подготовить два личных аккаунта

- [ ] Установить идентификаторы двух личных Google аккаунтов, их исходных
  календарей и аккаунта, из которого наблюдается доступность другого.
- [ ] Настроить способ доступа для эксперимента; пока ничего не настроено.
  Хранить секреты вне репозитория, в протокол включать только безопасные ссылки
  на хранилище и условные обозначения аккаунтов.
- [ ] Определить используемые способы планирования. Обязателен Google Calendar
  «Найти время» со стороны другого аккаунта; страницы бронирования и внешние
  инструменты проверяются, если пользователь ими пользуется.

## 2. Проверить гипотезу о вторичном календаре

- [ ] Провести протокол из [business/validation.md](business/validation.md)
  в обоих направлениях между двумя личными аккаунтами.
- [ ] Записать результат отдельно для каждого способа планирования, включая
  перенос, удаление и скрытие календаря копий.
- [ ] Удалить созданные тестом данные и восстановить изменённые настройки.
- [ ] Зафиксировать GO, NO-GO либо неполную проверку. При NO-GO предложить
  Busy-копии в основных календарях с явным описанием изменения UX; не реализовывать
  альтернативу автоматически.

## 3. Проверить доступ и применимость на четырёх аккаунтах

После успешного личного эксперимента, до эксплуатации на четырёх аккаунтах:

- [ ] Определить окончательные четыре аккаунта и сервисную учётную запись.
- [ ] Проверить sharing и фактическое чтение исходных данных на каждом аккаунте.
- [ ] Проверить создание, изменение и удаление сервисом собственных тестовых
  блоков в каждом календаре назначения; убедиться в сохранении результата.
- [ ] Повторить проверку доступности с рабочим аккаунтом назначения и наблюдением
  из реального рабочего сценария. Личный эксперимент этого не заменяет.
- [ ] Зафиксировать конкретные ограничения организаций. При блокере остановить
  затронутый вариант и предложить простейшую альтернативу для этого аккаунта.

## 4. Закрыть неоднозначности перед реализацией

Эти задачи не блокируют ручную проверку и работу CLI с явно выбранными
параметрами; окончательные продуктовые правила ещё требуют согласования.

- [ ] Согласовать правило событий на весь день: как исключать информационные
  события, помеченные Busy, сохраняя отпуск и реальную недоступность.
  Не распознавать смысл по заголовкам.
- [ ] Определить tentative: статус события, ответ пользователя «возможно»
  или оба случая; закрепить соответствие полям Google Calendar.
- [ ] Определить горизонт синхронизации будущих событий и обработку прошлого,
  включая длинные и повторяющиеся события на границе окна.
- [ ] До эксплуатации определить, как владелец узнаёт об остановке синхронизации.

Решения о событиях и горизонте после согласования перенести в BUSINESS.md;
эксплуатационное решение — в документацию запуска. CLI уже требует явную
all-day политику и горизонт; значения шаблона не считать согласованными правилами.

## 5. Проверить реальную эксплуатацию и релизную доставку

- [ ] После настройки пройти doctor, dry-run и запись с read-back на реальных
  аккаунтах; измерить целевую задержку, проверить перезапуск и все сценарии приёмки.
- [ ] Настроить правильный origin/GitHub repository для выпуска и update.
  Git remote пока отсутствует; RoTorEx/gallendar не найден при read-only проверке.
- [ ] Перед первым выпуском подтвердить сборки Intel macOS и Linux x86_64 на
  соответствующих runners; локальная Apple Silicon сборка не заменяет их.
- [ ] После отдельно запрошенного релиза прочитать результат GitHub Actions
  и опубликованные архивы, checksums и installer. Релиз сейчас не выполнен.
