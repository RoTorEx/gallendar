# Направление разработки

Пользователь уточнил результат: нужен рабочий Rust CLI, с теми же базовыми
командами и релизным процессом, что у соседей. CLI реализуется до проверки
гипотезы; переход к реальной эксплуатации требует доказательств доступности.
Текущая очередь внешних проверок и неоднозначностей — [TASK.md](TASK.md).

## Реализованный этап: CLI

Есть setup/config/home/version/update, offline demo, doctor, dry-run,
однократная и периодическая синхронизация. Движок фильтрует Free и отклонённые
приглашения, обрабатывает раскрытые Google повторения и исключения, сохраняет
Busy-копии по приватным меткам, восстанавливает соответствия после перезапуска
и проверяет результат записи чтением.

Доступны make check, сборка, локальная установка, упаковка, smoke install и
интерактивный release/release-push. Workflow готовит GitHub Releases для macOS
Apple Silicon/Intel и Linux x86_64. Наличие workflow не означает опубликованный
релиз или проверенные удалённые runners.

## 1. Проверка гипотезы — текущая внешняя работа

Начать с двух личных аккаунтов по [business/validation.md](business/validation.md).
Доступ пока не настроен; GO / NO-GO не установлен. Затем проверить sharing всех
четырёх целевых аккаунтов и реальные рабочие способы планирования.

GO личного эксперимента разрешает проверку рабочих аккаунтов; он не доказывает
работу четырёхаккаунтного решения. При NO-GO предложить копии в основных
календарях с явным изменением UX; не переключаться автоматически.

## 2. Подтверждение продуктовых правил

Уточнить all-day, значение tentative, горизонт и способ обнаружения остановки.
CLI уже позволяет явно задать политику и горизонт, не распознаёт смысл по
названию. Уточнения переводятся в правила и проверки только после согласования.

## 3. Реальная приёмка и автономная работа

Проверить полный путь от события источника до недоступности назначения на всех
четырёх аккаунтах. Пройти десять сценариев приёмки, измерить задержку до двух
минут, проверить сбой доступа, перезапуск и сохранение приватности.

После GO настроить периодический запуск на VPS и согласованный способ наблюдения
за сбоями. Команда run готова; работающий VPS ещё не настроен.

## 4. Релизная доставка

Настроить правильный origin и проверить остальные supported targets перед первым
отдельно запрошенным релизом. Выпустить через make release / make release-push,
проверить GitHub Actions и assets, затем update установленного CLI.

Веб-интерфейс, SaaS, другие провайдеры и общие запасные механизмы подключения
остаются вне MVP.
